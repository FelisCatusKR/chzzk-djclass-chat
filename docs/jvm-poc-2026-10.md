# JVM 이전 실험: Spring Boot · Quarkus (2026-10-12)

학습 목적으로 이 서버의 핵심 경로를 Spring Boot 4.1과 Quarkus 3.40(둘 다 Java 25)으로 각각 옮기고,
같은 Raspberry Pi 4에서 프로덕션 Go 이미지(`sha-d04d885`)와 똑같은 부하로 비교했습니다. **이전 계획은 없습니다.**
코드, 측정 도구, 전체 리포트는 별도 저장소에 있습니다:
[FelisCatusKR/chzzk-djclass-jvm-poc](https://github.com/FelisCatusKR/chzzk-djclass-jvm-poc)
([REPORT.md](https://github.com/FelisCatusKR/chzzk-djclass-jvm-poc/blob/main/REPORT.md)).

## 이 저장소에 주는 시사점

- 이 호스트와 "머지마다 재시작" 배포 방식에서는 Go가 여전히 가장 가볍습니다.
  - JVM 모드는 기동하는 동안(5~24초) 위젯이 끊깁니다.
  - 가장 가벼운 Quarkus 네이티브도 부하 중 최대 메모리가 Go의 약 2배입니다.
- 격차의 상당 부분은 언어가 아니라 프레임워크에서 왔습니다. 같은 JVM에서 Quarkus는 Spring보다 기동이
  1.7~3배 빠르고, 최대 메모리는 20~45% 적었습니다.
- 동시성 구조(요청당 블로킹 SSE 루프, 채널당 ingest/flush 워커)는 Java 21+ 가상 스레드로 거의 그대로 옮겨집니다.
  언어를 바꿔야 할 구조적인 이유는 없었습니다.
- 두 네이티브 이미지 모두, 프레임워크 밖에서 Jackson으로 직렬화하는 record를 자동으로 등록하지 못했습니다.
  - Spring에서는 `Error`가 flush 스레드를 죽여 채널이 조용히 멈췄습니다.
  - Quarkus에서는 배지가 있는 배치만 버려졌습니다.
  - Go `realtime`에도 같은 질문이 유효합니다: 배치 하나의 실패가 채널 전체를 멈추지 않는가? 현재
    `flushOnce`는 인코딩 오류를 로그로 남기고 넘어가며, resolver 오류는 `unlinked`로 강등합니다.
